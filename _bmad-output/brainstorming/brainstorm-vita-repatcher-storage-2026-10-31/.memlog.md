- (idea by user) User seed: list games with rePatch enabled/disabled status per game
- (idea by user) User seed: on enable, prompt to mount game files unencrypted and move them to chosen rePatch storage
- (idea by user) User seed: one global rePatch storage device, chosen at first launch
- (idea by user) User seed: detect rePatch folders on other devices and offer to migrate all to newly chosen device
- (direction) Audience: public release; stance: Creative Partner
- (direction) Drop Empathy Map; batch is Question Storming, Worst Possible Idea, SCAMPER
- (insight by user) Most users have SD2Vita as ux0; user's own setup: ux0 = memory card holding bubbles, SD2Vita mounts at uma0 via YAMT; disable YAMT + reboot + insert gamecard means uma0 disappears
- (technique) started Question Storming
- (question by coach) Does the rePatch plugin itself read from uma0:rePatch, or only ux0? If only ux0, does the app need a plugin fork or a path redirect?
- (question by coach) In gamecard mode with uma0 gone, what does LiveArea do when a ux0 bubble launches and its data lives on missing uma0: error, crash, black screen?
- (question by coach) Where do rePatch files for gamecard games live, if uma0 is absent whenever a gamecard is inserted?
- (insight by user) rePatch plugin scans a device list and uses the FIRST device that has a rePatch folder; uma0 works only if no rePatch folder exists on ux0
- (insight by user) Launching a ux0 bubble whose data is on missing uma0 gives an error; acceptable and expected
- (decision by user) Gamecard games are out of scope; no rePatching of gamecards
- (insight by coach) First-folder-wins means migration is mandatory, not optional: any rePatch folder on a higher-priority device silently shadows the chosen one
- (question by coach) What if an empty or stray ux0:rePatch folder appears (created by another tool or mod installer)? It would silently shadow all uma0 data
- (question by coach) What is the exact device scan order (ux0, uma0, imc0, grw0, xmc0...) and does it differ across rePatch versions/forks?
- (question by coach) Does reAddcont (DLC) follow the same first-folder-wins rule, and should the app manage it too?
- (idea by user) On launch, scan every storage device other than the chosen one for rePatch folders and flag them
- (insight by user) rePatch scan order from repatch.h: ux0, uma0, imc0, grw0, xmc0, ur0; folders managed: rePatch, reAddcont, reData
- (decision by user) reAddcont follows the same first-found rule; app manages reAddcont too
- (question by coach) Is the repatch.c lookup per-folder or per-file? It checks DEVICES[i]/filepath; if filepath is the full file path, priority is per file and ux0/uma0 could coexist per title
- (question by coach) Should reData also be managed by the app, alongside rePatch and reAddcont?
- (question by coach) Since ur0 is last in scan order, should ur0 even be offered as a storage choice?
- (direction by user) Correction: the stray-folder scan runs when the user opens the repatcher app, not when a game launches
- (decision by user) Ignore per-file vs per-folder lookup nuance; rule is simply: all rePatch data lives on the selected device only (keep it simple)
- (decision by user) App manages reData too (rePatch, reAddcont, reData)
- (decision by user) Storage picker shows every device that is both supported by rePatch AND currently mounted (ur0 included if mounted)
- (question by user) Interrupted copy (battery dies at 60%): how do we resume, and can we resume at all?
- (question by user) Original game still exists on source (likely ux0): how do we tell the user it is NOT safe to prune source files yet?
- (idea by user) Per-game manifest with SHA of every copied decrypted file; on next app launch compare last manifest entry's SHA to the file in the rePatch folder to detect an incomplete copy
- (question by user) Should the app prompt the user when it detects an unsuccessful previous run from what it sees on storage?
- (idea by coach) Write the full manifest (planned file list, sizes, hashes, state=copying) BEFORE copying; copy each file as name.part, verify, then rename; mark state=complete at end; resume = skip verified files, redo the .part
- (question by coach) Hashing GBs on the Vita CPU is slow: full SHA-256, cheaper CRC32, or size check plus hash only the last/partial file?
- (decision by user) Endorsed: manifest written up front, copy as .part then verify+rename, state=complete at end, resume skips verified files, prune blocked until complete. Hash algorithm still open
- (question by user) Do we ever prompt to prune? Users must test the game works first, so never prune right after copying
- (question by user) Do we only allow manual pruning of enabled games the app is managing?
- (question by user) Do we prune every file that was copied and is in the manifest?
- (idea by user) Selective prune: list files that are in the manifest AND still exist on original ux0, sorted by size descending, so user can prune only the biggest verified files
- (idea by coach) Per-game state machine: Copying -> Copied -> Tested (user taps 'I played it, it works') -> Prunable; prune actions unlock only at Tested
- (idea by coach) Protected list: files the bubble/system needs on ux0 never appear in the prune list
- (question by coach) Which ux0:app files must stay for the bubble to launch (eboot.bin, sce_sys, sce_pfs?), and does a pruned file need a zero-byte stub?
